Persistent storage in OpenShift

Developers ask for storage - the platform provides it

One picture for the whole session. On the left, what a developer controls: a pod mounts a volume, and the volume comes from a PersistentVolumeClaim - a request: "1 GiB, mounted by one node at a time, from this class of storage". On the right, what the platform team controls: StorageClasses are the menu of storage on offer; each one names a CSI driver, the adapter between OpenShift and the actual storage - OpenShift Data Foundation today, but just as well a SAN, a NAS or a cloud provider's disks. When a claim arrives, the driver creates the volume on the storage, a PersistentVolume object appears to represent it, and it's bound to the claim. Nobody opened a ticket. If the audience is new to these words, press DOWN for one slide per concept; otherwise go RIGHT to the demo and explain them as they show up.

Ephemeral by default

A container's own files - and an emptyDir - live and die with the pod.

In the demo: Part 1

Every container gets a writable layer on top of its image, and a pod can add an emptyDir volume for scratch space. Both live on the node and are deleted with the pod. And pods get replaced all the time: a rollout, a node drain for an upgrade, a crash, a scale-down. So anything an application writes there is gone at the next restart. That's the default - and it's a feature: stateless pods are what make self-healing and scaling easy. Data you want to keep needs a persistent volume.

PV & PVC

The claim is the request, in your project.
The volume is the real thing, cluster-wide.

In the demo: Parts 2 and 3

A PersistentVolumeClaim is a namespaced object a developer writes: size, access mode, storage class. A PersistentVolume is the cluster-wide object that represents a real piece of storage - a Ceph block image, an NFS export, a cloud disk. Developers normally can't even list PVs; they only see their claims. Binding is one-to-one. Pods mount claims, never PVs directly, so the same pod spec works on any cluster. The reclaim policy decides what happens when the claim is deleted: Delete (the default for dynamic storage - the data goes too) or Retain.

Static or dynamic

Static: an admin makes volumes in advance; a claim takes one.
Dynamic: the claim makes its own.

In the demo: NFS in Part 2, ODF in Part 3

Two ways a claim finds its volume. Static provisioning is the original Kubernetes model: an administrator creates PersistentVolumes in advance - here, ten directories on a plain NFS server - and each claim is bound to one that's big enough and has the right access mode. No storage system, no driver, no API; but someone has to keep the shelf stocked, a claim gets a whole PV even if it asked for less, and a released PV needs manual cleanup before it can be reused. Dynamic provisioning adds a StorageClass with a provisioner: every claim gets a volume made to measure, on demand, and it's deleted when the claim is. That's what ODF - or any CSI driver with a provisioner - does. Most clusters use dynamic storage for everything; static PVs survive for existing NFS shares and special cases.

StorageClass

The menu: which driver, which settings.
Volumes are made on demand.

In the demo: Part 3

A StorageClass names a provisioner (the CSI driver) and its parameters: which pool, which filesystem, encrypted or not, what happens on delete, whether volumes can grow. One class is marked default - a claim that doesn't name a class gets that one (our demo's claims always name theirs). With ODF we get three: Ceph RBD for block volumes, CephFS for shared file volumes, and NooBaa for S3 buckets. The point for operations: the platform team decides what's on the menu. Developers pick from it by name; the same claim, unchanged, gets a vSphere disk on one cluster and a Ceph volume on another.

Access modes

Who may mount the volume at the same time

RWO

ReadWriteOnce

One node at a time. Block storage. Pods on that same node can share it.

RWX

ReadWriteMany

Many nodes, read and write. Shared file storage: CephFS, NFS.

ROX

ReadOnlyMany

Many nodes, read only. Reference data.

RWOP

ReadWriteOncePod

Exactly one pod, cluster-wide. The strict RWO.

In the demo: Parts 4 and 5

The access mode is a promise the storage has to keep. RWO, ReadWriteOnce, is the common one - block storage attached to one node. Note the trap: it's one NODE, not one pod; two pods on the same node can both mount it, which surprises people. ReadWriteOncePod is the strict version. RWX, ReadWriteMany, needs a shared filesystem - CephFS or NFS - so pods on different nodes can all read and write. ReadOnlyMany is for shared reference data. Rule of thumb: databases want RWO block storage (and replicate themselves if they need more copies); RWX is for content that several pods really share, like uploads. Raw block volumes in RWX mode exist too - OpenShift Virtualization uses them for live migration.

CSI

Container Storage Interface: one standard plug for every storage vendor.

In the demo: every volume

Storage drivers used to be compiled into Kubernetes. CSI moved them out: each vendor ships a driver, installed as an operator, that runs as pods on the cluster. A controller part talks to the storage's API - create, delete, snapshot, expand - and a node part on every worker attaches, formats and mounts the volume for the pods on that node. Why ops should care: what you can do with a volume (snapshots, online expansion, RWX, encryption) depends on the driver, not on OpenShift. Read the driver's feature list before you pick storage; "it has a CSI driver" is necessary, not sufficient.

Local storage

A disk inside one node: fast, but the data can't follow the pod.

Use it for: software that replicates its own data - like ODF itself

Local volumes - the Local Storage Operator, LVM Storage, hostPath - use a disk inside one node. Fast and cheap, but the PV carries node affinity: the pod can only ever run on that node. If the node dies, the pod stays Pending and the data is unreachable; even a planned drain for an upgrade gets stuck. Avoid it for applications. It's the right choice for software that keeps its own replicas across nodes - Kafka, some databases, and ODF itself, which builds its replicated storage out of the nodes' local disks. Single-node OpenShift at the edge is the other exception.

Object storage

Buckets over HTTPS (S3) - not a filesystem.
Ask for one with an ObjectBucketClaim.

In the demo: backups land in a bucket (Part 9)

Object storage stores whole objects in buckets, read and written over HTTPS with the S3 API - no mounting, no file locking, practically no size limit. It's where backups, logs, images and data-lake files go. ODF provides it through the Multicloud Object Gateway (NooBaa), and the Ceph object gateway on bare metal. A developer asks for a bucket the same self-service way as a volume: an ObjectBucketClaim. In return they get the bucket plus a Secret with the access keys and a ConfigMap with the endpoint, ready to inject into a pod. Today it's where OADP puts our backups.

Snapshot ≠ backup

A snapshot is a point in time, on the same storage.
A backup leaves the cluster.

In the demo: Parts 8 and 9

A CSI snapshot is a VolumeSnapshot object: a point-in-time copy made by the storage itself, in seconds, usually copy-on-write. Restoring it means creating a new PVC from it. Great for "undo" before an upgrade or after a bad script. But it lives on the same storage: if the storage cluster is lost, so are its snapshots. A backup copies data out - to object storage in another place - together with the Kubernetes objects that use it (Deployments, Secrets, Routes...), so you can rebuild a whole project, on this cluster or another one. That's OADP, the OpenShift API for Data Protection, built on the Velero project. You want both.

OpenShift Data Foundation

Block, file and object storage, built from the cluster's own disks - and run like any other operator.

In the demo: Part 6

OpenShift Data Foundation is Red Hat's software-defined storage for OpenShift. Internally it's Ceph, deployed and run by the Rook operator, plus the Multicloud Object Gateway (NooBaa) for S3. In "internal" mode it turns local disks in three or more nodes into one replicated pool - every write lands on three nodes, so losing a node loses no data. In "external" mode it connects OpenShift to an existing Ceph cluster. What it adds on top of a plain CSI driver - and what we'll look at in Part 6: all three storage types from one product, snapshots, clones, online expansion, encryption, capacity and performance dashboards in the console, storage health alerts, and disaster recovery across clusters together with Advanced Cluster Management.

Live demo: today's setup

One small app - a logbook - on plain NFS, then three ways on ODF

The application doesn't matter today, so it's tiny: a "logbook". Every pod writes a line every five seconds - the time, its own pod name and the node it runs on - into /data/logbook.txt, and serves that directory over HTTP. So in the browser you can see who wrote what, and whether the history survives. We run it three ways: a Deployment with one pod (first without storage, then on a static NFS volume, then on an ODF block volume), a DaemonSet - one pod on every node - all sharing one file volume, and a StatefulSet that gives each replica its own disk. Underneath, ODF provides the block, file and object storage; on the right, the operations side - an alert when a volume fills up, and a backup of the whole project to an ODF bucket. 1 · Ephemeral by default

The app writes - the pod is replaced - the history is gone

  1. Topology: logbook - one pod, a line every 5 s
  2. Its Route: /logbook.txt - who wrote what
  3. Delete the pod - a new one starts
  4. Reload: a new pod name, the history is gone
  5. Deployment → Volumes: data, no type - nothing behind it

The same, as code

curl -s $LOGBOOK_URL/logbook.txt | tail -3
oc delete pod -l app=logbook
curl -s $LOGBOOK_URL/logbook.txt
oc set volume deployment/logbook
Show it, don't explain it: the proof is what happens to the data. The logbook Deployment is pre-staged by setup (manifests/logbook-ephemeral.yaml). Topology (Developer perspective, project demo-storage) → logbook → open the Route (arrow icon) and add /logbook.txt: lines like "10:42:05 logbook-7d9f…-x2k4p on ocpnode3". Reload a couple of times - it grows. "This is the app's data - and every line says which pod wrote it." Note the pod name. Delete the pod: Topology → logbook → side panel → the pod → Actions → Delete Pod. The Deployment starts a new one within seconds (the ring goes light blue, then dark blue). Reload: a NEW pod name, and the history starts just now - everything the old pod wrote is gone. "Every rollout, node drain for an upgrade, or eviction does exactly this. Pods are disposable - that's what makes self-healing and scaling easy - so data you want to keep can't live in the pod." Why: click the Deployment name in the side panel → Details, scroll to Volumes: one volume, data at /data - and the Type column is empty. "There's a volume, but nothing behind it: it's an emptyDir, a scratch folder the pod gets on its node and loses with the pod. Remember this row - in Part 2 it gets a type." (The console has no label that says "ephemeral"; the blank Type is the tell.) If asked "so where is the data?": Deployment → YAML tab, volumes: data → emptyDir: {}. For an ops audience, the node itself (as peter): Pod → Details → Node; Compute → Nodes → that node → Terminal tab: chroot /host find /var/lib/kubelet/pods -path '*empty-dir/data/logbook.txt' | xargs tail -2 "A folder in the kubelet's area on that node." Delete the pod, run the find again: gone. Careful with "restart": an emptyDir survives a container RESTART in the same pod (a crash, a failed liveness probe). It's lost when the POD is replaced - deleted, rescheduled, or rolled out. Press DOWN for the backup screenshot.

2 · Static volumes: plain NFS

The admin stocked the shelf - a claim takes a whole volume

  1. Storage → PersistentVolumes: nfs-pv1 … 10, Available
  2. Claim 1.5 GiB of nfs-static - bound to a 2 GiB PV
  3. Mount it in the logbook - delete the pod - the history stays
  4. df: a "2 GiB" volume shows 100 GiB - the size is only a label
  5. Claim 10 GiB: Pending - nothing on the shelf fits

The same, as code

oc get pv -l storage=nfs-static
oc create -f nfs-claim.yaml
oc get pvc nfs-claim
oc set volume deployment/logbook --add \
  --overwrite --name=data \
  --type=pvc --claim-name=nfs-claim
oc delete pod -l app=logbook
oc exec deployment/logbook -- df -h /data
oc create -f nfs-claim-big.yaml
oc describe pvc nfs-claim-big
As peter, Administrator perspective. Storage → PersistentVolumes, filter "nfs": ten volumes nfs-pv1…10 - 1 GiB (1-5), 2 GiB (6-8) and 5 GiB (9-10), all Available, class nfs-static, reclaim policy Retain. Open one → YAML: spec.nfs.server and path - "a directory on an ordinary NFS server. Setup created them; in real life that's a ticket to the storage team." Storage → StorageClasses → nfs-static: provisioner kubernetes.io/no-provisioner - "a label for the shelf; nothing behind it creates volumes". (Not the default class - claims name it.) As user1: oc create -f nfs-claim.yaml - 1.5 GiB, RWX, class nfs-static. Bound within seconds - to a 2 GiB PV (6, 7 or 8): "the binder picks the smallest volume that fits, and I get all of it". Swap the logbook onto it: oc set volume deployment/logbook --add --overwrite --name=data --type=pvc --claim-name=nfs-claim Reload, delete the pod, reload: the history survived. Now the catch: oc exec deployment/logbook -- df -h /data shows ~100G - the whole file system on the server, not 2 GiB. "OpenShift picked this PV by its label - 2Gi - but nothing enforces it. All ten PVs share the same 100 GiB, so one runaway app fills it for every claim, and for everyone else using that server." The PVC page's Used/Available and the kubelet metrics see the same 100 GiB, so a fill alert on an NFS claim measures the shared disk, not the claim. Enforcing a size takes quotas on the server, or storage with a provisioner (Part 3: df on an ODF volume shows exactly what was asked). Never run the Part 7 fill on an NFS claim. Optional, on the NFS server: ls -ln the pvX directory - logbook.txt is right there, a plain file, owned by 3000:3000 whatever pod wrote it (the export squashes every client user to one ID): plain NFS can't tell projects apart; the only boundary is which directory the admin put in each PV. Now ask for more than the shelf has: oc create -f nfs-claim-big.yaml (10 GiB). Pending; oc describe: "waiting for a volume to be created either by the external provisioner kubernetes.io/no-provisioner or manually by the system administrator". "Static storage means someone has to stock the shelf." oc delete -f nfs-claim-big.yaml. The PV filter as user1: oc get pv - Forbidden; developers only see their claims. 3 · Dynamic storage: ODF

Pick from the menu - the volume makes itself

  1. Storage → StorageClasses: the menu
  2. PersistentVolumeClaims → Create: logbook-data, ceph-rbd, 1 GiB, RWO
  3. Bound - a PV appeared by itself
  4. Move the logbook from NFS to this claim
  5. Delete the NFS claim: its PV is Released, not free

The same, as code

oc get storageclass | \
  grep -E '^NAME|openshift-storage'
oc create -f logbook-data-pvc.yaml
oc get pvc logbook-data
oc set volume deployment/logbook --add \
  --overwrite --name=data \
  --type=pvc --claim-name=logbook-data
oc delete pvc nfs-claim
oc get pv -l storage=nfs-static
Administrator perspective. Storage → StorageClasses: three from ODF - ocs-storagecluster-ceph-rbd (block), -cephfs (file) and openshift-storage.noobaa.io (object) - plus whatever else the cluster has (the ★ default is whatever it is; our claims always name their class). Look only - this ODF is shared; the demo never edits a class. Open ceph-rbd: provisioner openshift-storage.rbd.csi.ceph.com, reclaim policy Delete, allow volume expansion true (Part 7 needs it). Storage → PersistentVolumeClaims → Create PersistentVolumeClaim (project demo-storage): StorageClass ocs-storagecluster-ceph-rbd, name logbook-data, access mode Single user (RWO), size 1 GiB, volume mode Filesystem. Create. Status Pending → Bound within seconds. Click the PersistentVolume link: a pvc-… object, cluster-scoped, made by the CSI driver - "nobody filed a ticket". Developers can do this too: in the user1 tab, oc get pvc works, and oc get pv says Forbidden - claims are theirs, volumes are the platform's. Mount it instead of the NFS claim, as code (no console form replaces an existing volume): oc set volume deployment/logbook --add --overwrite --name=data --type=pvc --claim-name=logbook-data The Deployment rolls out a new pod. The strategy is Recreate on purpose: with RWO, a rolling update could start the new pod on another node while the old one still holds the disk, and it would hang (Part 4 shows that error). Reload the logbook, delete the pod, reload: the old pod's lines are still there, followed by the new pod's. "The pod is disposable; the claim is not." (This logbook starts fresh: the NFS history stays on the NFS volume.) The contrast with static storage: oc delete pvc nfs-claim (user1). As peter, Storage → PersistentVolumes: that nfs-pvX is now Released - not Available. Reclaim policy Retain: the data is still on the NFS server, and before anyone can use that PV again an admin must wipe the directory and clear the PV's claimRef. A dynamic ODF volume (reclaim Delete) simply disappears with its claim. If asked "can't NFS clean up by itself?": the old reclaim policy Recycle (rm -rf, then Available again) - deprecated for years, don't build on it. Today's answer is a provisioner: the community csi-driver-nfs (or the older nfs-subdir-external-provisioner) creates a directory per claim on an existing NFS export and deletes it with the claim. Community projects, not supported by Red Hat, and they need privileged node pods - but it's exactly the point: a StorageClass with a provisioner turns the shelf into dynamic storage, which is what ODF did for us here. 4 · One volume, many pods: RWO vs RWX

A block disk follows one node - a shared file system serves them all

  1. logbook-rwo: 3 pods on 3 nodes, one RWO claim
  2. One Running, two stuck: Multi-Attach error
  3. logbook-rwx: a DaemonSet - a pod per node - one CephFS claim
  4. Its Route: every node writes to the same logbook

The same, as code

oc create -f logbook-rwo.yaml
oc get pods -l app=logbook-rwo -o wide
oc get events \
  --field-selector reason=FailedAttachVolume
oc delete -f logbook-rwo.yaml

oc create -f logbook-rwx.yaml
oc get pods -l app=logbook-rwx -o wide
curl -s $LOGBOOK_RWX_URL/logbook.txt | tail
"What if I scale my logbook to three pods?" In the user1 tab: oc create -f logbook-rwo.yaml - a claim on ceph-rbd (RWO) and a Deployment with 3 replicas that must land on different nodes (pod anti-affinity, so the demo is predictable). oc get pods -l app=logbook-rwo -o wide: one Running, two ContainerCreating, forever. Console: one stuck pod → Events: "Multi-Attach error for volume pvc-… Volume is already used by pod(s) logbook-rwo-…". "RWO means one NODE. A block device can't be mounted read-write by two machines - the filesystem would be corrupted. Note: two pods on the SAME node would both have started - RWO isn't one pod; ReadWriteOncePod is." Clean up: oc delete -f logbook-rwo.yaml. Now shared storage: oc create -f logbook-rwx.yaml - a claim on ocs-storagecluster-cephfs with ReadWriteMany, and a DaemonSet: "one pod on every worker - typically used for agents like log collectors; today it's the clearest way to show many nodes on one volume". Topology shows the DaemonSet (DS) ring with one pod per worker. oc get pods -o wide: each on a different node, all Running. Open the logbook-rwx Route, /logbook.txt: lines from every pod and every node, interleaved, in one file. Reload - the Service sends you to a different pod each time, and the content is the same. When to use which: RWO block for databases (faster, and they handle their own replication); RWX file for content several pods really share - uploads, shared config, CMS content. Say it about our own demo: "every pod appends to the SAME file - fine for a demo, CephFS serializes the writers; on NFS lines could overwrite each other. A real app gives each pod its own file, or uses a database." If asked how RWX handles concurrency: it doesn't - RWX only allows the mounts. Coordination is the filesystem's and the app's job. CephFS keeps clients coherent (the metadata server revokes caching when several write one file) and coordinates POSIX locks (fcntl/flock) across nodes; NFS v4 is only close-to-open consistent, with lease-based locks. Locks are advisory - they only work if every writer uses them - and nothing detects deadlocks between pods on different nodes: that's the app's design (one lock order, timeouts, or no shared write locks at all). What the storage does: a dead client's locks are released - CephFS evicts and fences (blocklists) it, NFS lets its 90 s lease expire. Good RWX: many readers, or writers that each write their own files. Bad RWX: several writers updating the same file without locking; never a database's data directory shared by replicas (SQLite on NFS is the classic failure) - databases use RWO per replica (Part 5). RWX block for VM live migration is safe because the hypervisor guarantees one writer. Press DOWN for backup screenshots.

5 · StatefulSet: a disk per replica

Stable names, stable disks - how databases scale

  1. logbook-sts: 3 replicas, a claim template
  2. Three PVCs: data-logbook-sts-0, -1, -2
  3. Each pod: its own logbook
  4. Delete logbook-sts-1 - same name, same disk
  5. Scale to 1 - the claims stay

The same, as code

oc create -f logbook-sts.yaml
oc get pods,pvc -l app=logbook-sts
oc exec logbook-sts-1 -- \
  tail -3 /data/logbook.txt
oc delete pod logbook-sts-1
oc scale statefulset/logbook-sts \
  --replicas=1
oc get pvc -l app=logbook-sts
oc create -f logbook-sts.yaml (user1). The StatefulSet has a volumeClaimTemplates section instead of a volume: "a recipe for a claim, used once per replica". Pods come up as logbook-sts-0, -1, -2 - fixed names, not random suffixes - and Storage → PersistentVolumeClaims shows data-logbook-sts-0, -1, -2, all RWO ceph-rbd, each bound to its own PV. Each pod has its own logbook: logbook-sts-1 → Terminal → tail /data/logbook.txt - only logbook-sts-1's lines. Delete logbook-sts-1: it comes back with the SAME name, possibly on another node, and reattaches the SAME claim - tail again: the old lines are still there. "Identity and disk travel together." oc scale statefulset/logbook-sts --replicas=1: pods -2 and -1 go away (highest first), the claims stay - scale back up and they reattach. Deleting the StatefulSet doesn't delete them either (by default): "storage is deleted on purpose, never by accident". This is how PostgreSQL, Kafka or Elasticsearch operators run their members: each replica its own RWO volume, replication in the software. Then, while you go to the dashboards - fill the volume for Part 7 now, it takes a couple of minutes for the alert to fire (cheat 7 shows the lines): oc create -f logbook-volume-alert.yaml, then oc exec deployment/logbook -- dd if=/dev/zero of=/data/ballast bs=1M count=900 Press DOWN for the backup screenshot.

6 · What ODF adds

Storage you can see - capacity, performance, health

What a typical external CSI driver gives you versus ODF. Any decent driver does dynamic provisioning of block volumes; the rest "depends" on the vendor and the array - and the visibility and alerting live in the vendor's own tool, not in OpenShift. Many sites use both: the SAN's CSI driver for some workloads, ODF for the rest and for object storage.

7 · A volume fills up

Get warned early - then grow it without downtime

  1. An alert at 80% full - as code
  2. Fill logbook-data: 900 MiB
  3. How full? df in the pod - the console, only if the driver reports it
  4. Observe → Alerts: VolumeAlmostFull fires
  5. PVC → Expand PVC: 2 GiB, online
  6. The alert resolves - the pod never restarted

The same, as code

oc create -f logbook-volume-alert.yaml
oc exec deployment/logbook -- dd \
  if=/dev/zero of=/data/ballast bs=1M count=900
oc exec deployment/logbook -- df -h /data
oc patch pvc logbook-data --type=merge \
  -p '{"spec":{"resources":{"requests":{"storage":"2Gi"}}}}'
oc exec deployment/logbook -- df -h /data
oc exec deployment/logbook -- rm /data/ballast
The first two lines ran at the end of Part 5 (if not, run them now and talk through the rule while waiting ~2-3 min). Show the rule: logbook-volume-alert.yaml - a PrometheusRule in OUR project: kubelet_volume_stats_used_bytes / kubelet_volume_stats_capacity_bytes > 0.8 for 1 minute → VolumeAlmostFull, severity warning. "Alerts are code too - the app team owns this one, in its own namespace, with its own threshold." (User workload monitoring is enabled by setup; user1 has the monitoring-rules-edit role.) How full is it? The reliable answer is df inside the container: logbook pod → Terminal tab → df -h /data (or oc exec deployment/logbook -- df -h /data): ~92% used. The console's PVC page (Storage → PersistentVolumeClaims → logbook-data: the Available donut and Used) and the kubelet metrics only show usage when the storage driver reports volume stats for that volume - CSI drivers may or may not, raw block volumes never do, and what's reported depends on the filesystem. "Don't build your capacity process on the console's number; df in the container is the truth." ODF's RBD and CephFS volumes do report, which is what makes the Part 7 alert possible - with another driver, check first. The PVC page also shows only the current value (no history; history is Observe → Metrics, kubelet_volume_stats_used_bytes{persistentvolumeclaim="logbook-data"}), and a nearly empty volume shows "Used 0 B". The ODF dashboards are cluster-wide (capacity, performance, prediction), not per claim. Developer perspective → Observe → Alerts: VolumeAlmostFull firing for logbook-data. (Admin: Observe → Alerting shows it too.) The alert is built on the kubelet's volume stats, which ODF's driver reports - say so: "this works because the driver reports usage; with storage that doesn't, you'd alert from inside the app or the storage system, and check with df". Fix it: Administrator → Storage → PersistentVolumeClaims → logbook-data → Actions → Expand PVC → 2 GiB → Expand. Watch the PVC: the size changes in seconds; df -h /data in the pod: 2.0G, ~45% used. The pod was never restarted - the CSI driver grew the Ceph image and the node plugin grew the filesystem online (needs allowVolumeExpansion: true on the class). Within a minute or two the alert resolves. "You can only grow, never shrink." Remove the ballast (oc exec deployment/logbook -- rm /data/ballast) before Part 8. Press DOWN for backup screenshots.

The alert, as code

- alert: VolumeAlmostFull
  expr: |
    kubelet_volume_stats_used_bytes
      / kubelet_volume_stats_capacity_bytes > 0.8

8 · Snapshots: an undo button

A point in time, in seconds - restored as a new claim

  1. PVC logbook-data → Create snapshot
  2. "Oops": delete the logbook
  3. Snapshot → Restore as new PVC
  4. Point the Deployment at the restored claim
  5. The history is back

The same, as code

oc create -f logbook-snapshot.yaml
oc get volumesnapshot
oc exec deployment/logbook -- \
  rm /data/logbook.txt
oc create -f logbook-data-restored-pvc.yaml
oc set volume deployment/logbook --add \
  --overwrite --name=data \
  --claim-name=logbook-data-restored
Storage → PersistentVolumeClaims → logbook-data → Actions → Create snapshot: name logbook-data-snap, snapshot class ocs-storagecluster-rbdplugin-snapclass → Create. Storage → VolumeSnapshots: Ready in a few seconds - "however big the volume, the storage does copy-on-write". The mistake: oc exec deployment/logbook -- rm /data/logbook.txt. Reload the Route: only the last few seconds of lines. "Someone ran the wrong script." Restore: VolumeSnapshots → logbook-data-snap → Actions → Restore as new PVC: name logbook-data-restored, same class, size 2 GiB (at least the snapshot's size) → Restore. Bound. A snapshot never overwrites the original; you get a new claim and point the app at it (as code - same command as Part 3): oc set volume deployment/logbook --add --overwrite --name=data --claim-name=logbook-data-restored New pod, reload: the full history up to the snapshot is back, then new lines. Delete the old claim when happy. For a StatefulSet the claim name is the contract: scale to 0, delete data-logbook-sts-0, create a claim with that name from the snapshot, scale back up. Snapshots are taken by the storage, not the app: for a database, quiesce it or use its own backup tool for a consistent copy (OADP hooks can do that). Press DOWN for the backup screenshot.

When storage goes wrong

Most problems show up in three places: the claim, the pod's events, the storage

  1. PVC Pending: no default class, a typo, quota, no capacity
  2. Pod stuck ContainerCreating: Multi-Attach, mount errors
  3. App errors, disk full: usage metrics, df
  4. Everything slow or stuck: the ODF health and alerts

First looks

oc describe pvc <name>
oc get events --sort-by=.lastTimestamp
oc describe pod <name>
oc get volumeattachment | grep <pv>
oc exec <pod> -- df -h /data
oc get storagecluster,cephcluster \
  -n openshift-storage
oc adm must-gather --image=\
  registry.redhat.io/odf4/odf-must-gather-rhel9:v4.22
A short checklist, built from what we saw today. A claim stuck in Pending: oc describe pvc - its events say why: no default storage class and none named, a misspelled class, a project quota on storage, or the backend out of space. (With a WaitForFirstConsumer class, Pending is normal until a pod uses the claim.) A pod stuck in ContainerCreating: describe the pod - Multi-Attach (Part 3), a mount or permission error, a node that can't reach the storage. VolumeAttachments show which node holds a volume. An app failing with "no space left": df in the pod first - it's the reliable number; the PVC page's Used and the kubelet metrics only exist when the driver reports volume stats (Parts 6 and 7). If many volumes misbehave at once, look at the storage itself: the ODF dashboard and its alerts (Part 6). For a support case, run must-gather with the ODF image (match the tag to your ODF version) and attach the result.

What we just did

The plan from the start - in OpenShift terms

  • Ephemeral by default - emptyDir and the container layer
  • Static NFS PVs, then PVC → StorageClass → PV through CSI
  • RWO vs RWX - and StatefulSets for a disk per replica
  • OpenShift Data Foundation: block, file, object, dashboards, alerts
  • A PrometheusRule on volume usage - online PVC expansion
  • VolumeSnapshots to undo, OADP backups to recover
The same six points as "What we will cover today", with the names you saw on screen. A pod's own files are ephemeral; a PersistentVolumeClaim takes a pre-made PV from the shelf (static NFS), or asks a StorageClass for one and the CSI driver creates it (dynamic, ODF). RWO block volumes belong to one node - StatefulSets give each replica its own - while RWX file volumes are shared. ODF provides all three storage types plus the dashboards and alerts; we added our own alert as code, grew a volume online, undid a mistake with a snapshot and rebuilt the whole project from an OADP backup.
