From servers to OpenShift

The same questions - asked per container, answered by the platform

One slide to connect today's topic with what you already do with virtual machines. A VM can have physical CPU and memory reserved for it on the host - guaranteed, whatever else runs there. That's a request: the scheduler only places a pod where its requests fit. A VM is configured with a number of vCPUs and an amount of memory - the most the guest can ever use. That's a limit, enforced by the kernel on the node. Overcommit is the same idea too. A hypervisor lets you configure more vCPU and memory than the host physically has, betting that not every VM is busy at once. In OpenShift the requests must always fit the node - those are guaranteed - and the room between a pod's request and its limit is the overcommitted part: shared with every other pod on the node, first come, first served. Departments get budgets and disk quotas; projects get quotas. Monitoring is built in. And instead of resizing a machine, you let autoscalers add copies or recommend a better size. Requests

What a container is guaranteed.
The scheduler only places a pod where its requests fit.

In the demo: Parts 1 and 2

A request is a reservation. The scheduler adds up the requests of the pods already on each node and only places a new pod where its requests still fit in the node's allocatable capacity - the node's size minus what's kept back for the operating system and the kubelet. It doesn't look at actual usage at all. Two consequences. A pod with no requests can land anywhere, even on a full node. And a request that's far too big wastes capacity: the cluster looks full on paper while the processors sit idle. That gap between reserved and used is the first thing we'll look at in the demo.

Limits

The ceiling a container can't pass.
Enforced by the kernel, on the node.

In the demo: Parts 2 and 3

A limit is a hard cap, enforced by Linux cgroups on the node - the same mechanism you may already use on servers. Between its request and its limit, a container can use whatever happens to be free on the node. Above the limit, it's stopped - and how it's stopped depends on the resource, which is the next slide. Limits are optional. A container with a memory limit but no CPU limit is a common and sensible choice; we'll see why in Part 3.

One pod, three numbers

A node's memory - and where one pod's used, min and max sit in it

One node, seen from the memory side. The whole box is the node's physical memory. A slice on the left is kept back for the operating system and the kubelet; the rest is allocatable - what pods can reserve. Other pods have already reserved their share. Our guestbook pod has three numbers. Used: what it holds right now. Min, the request: memory guaranteed to it, and the only number the scheduler looks at when it places the pod - the solid part of the box is what it took from the node. Max, the limit: the pod may grow into the dashed part, but that room isn't reserved - it's shared with every other pod on the node, first come, first served. That's overcommit. If the pod goes past its limit, the kernel kills it: OOMKilled. And if the node runs short while the pod is in that shared room, it's among the first to be evicted. Set the request to what the pod really needs, and for anything important, request equal to limit removes the shared part altogether. The values are the ones the guestbook gets in Part 2 (used is an example). In the demo: Parts 1, 2 and 3.

CPU bends, memory breaks

Too much CPU: the container is slowed down.
Too much memory: it's killed.

In the demo: Part 3

CPU is a compressible resource: if a container wants more than its limit, the kernel simply gives it less time - it gets slower but keeps running. Memory isn't compressible: you can't take memory back from a process, so a container that goes over its memory limit is killed - the famous OOMKilled, exit code 137 - and restarted. That's also why overcommit works differently for the two. Requests are guaranteed; everything between a pod's request and its limit is shared room on the node, and the limits together can add up to more than the node has. For CPU that's harmless: busy containers just share. For memory, if several pods use that shared room at once, the node runs out and starts evicting pods that are over their requests. Common advice: for databases and anything that matters, set the memory request equal to the limit.

Quality of service

How requests and limits are set decides who goes first when a node runs short

Guaranteed

requests = limits

CPU and memory, every container. Evicted last.

Burstable

requests < limits

A reservation, plus room to grow. The usual choice.

BestEffort

nothing set

No reservation at all. Evicted first.

Eviction

node under pressure

BestEffort, then Burstable over their requests, then the rest.

In the demo: Parts 1 and 2

OpenShift sorts every pod into one of three quality-of-service classes, based only on how its requests and limits are set. Guaranteed: every container has CPU and memory requests equal to their limits. Burstable: at least a request is set, and limits are higher or missing - most applications. BestEffort: nothing set at all. The class matters when a node runs out of memory: the kubelet evicts BestEffort pods first, then Burstable pods that use more than they asked for. A pod that stays within its request is safe. Our guestbook starts the demo as BestEffort - the class nobody wants in production.

Quotas & limit ranges

A quota is the project's budget.
A limit range sets defaults and bounds per container.

In the demo: Part 4

A ResourceQuota caps the total for a project: CPU and memory requests and limits, number of pods, number of claims, storage per storage class. Anything that would take the project over its budget is refused when it's created - the existing pods keep running. It's the "department budget" of the platform. A LimitRange works per container: it fills in a default request and limit for containers that don't set any, and rejects ones outside a minimum and maximum. The two go together: once a quota covers CPU or memory, every pod must state those values - the LimitRange's defaults make sure it does.

Scale out, not up

More small pods beat one big pod.
Let the autoscalers do the sizing.

In the demo: Part 6

The old reflex is to give an application one bigger machine. In OpenShift the better answer is usually more copies: a HorizontalPodAutoscaler adds pods when the average usage passes a target and removes them when load drops - so the cluster only reserves the extra capacity while it's needed. It also spreads the risk: losing one of six small pods hurts less than losing one big one. The VerticalPodAutoscaler looks at what pods actually use and recommends requests - an optional operator we only mention today. On clouds and some bare-metal setups the cluster autoscaler adds nodes when pods can't be scheduled. Cost Management, on console.redhat.com, gives the same kind of recommendations across clusters, with cost.

Virtual machines too

A VM runs inside a pod.
Its CPU and memory become that pod's requests.

In the demo: Part 7

With OpenShift Virtualization a virtual machine runs inside a pod called virt-launcher, so everything from today applies to VMs as well: the scheduler places them by their requests, quotas count them, and the same dashboards show their use. The translation has two defaults worth knowing. CPU is overcommitted: by default each vCPU requests a tenth of a core, because most VMs are idle most of the time (the ratio is a cluster setting). Memory is not overcommitted by default: the pod requests the guest's memory plus an overhead for the virtualization layer. Higher density through memory overcommit exists, but it's an opt-in. Check the numbers against the release in use before quoting them.

3 · Hitting the ceiling

Over the CPU limit: slower. Over the memory limit: killed.

  1. A pod that keeps eating memory: OOMKilled, restarted
  2. Give the guestbook a tight CPU limit
  3. Put load on it: response times climb, throttling shows
  4. Roll back - and why many teams set no CPU limit

The same, as code

oc create -f memory-hog.yaml
oc get pod memory-hog -w
oc describe pod memory-hog | \
  grep -A 4 'Last State'
oc delete -f memory-hog.yaml

oc set resources deployment/guestbook \
  --limits=cpu=100m
ab -k -c 10 -t 60 https://$(oc get route \
  guestbook -o jsonpath='{.spec.host}')/
oc rollout undo deployment/guestbook
DRAFT. As user1. oc create -f memory-hog.yaml - a small pod that allocates memory in a loop, with a 128Mi limit. oc get pod memory-hog -w: Running → OOMKilled → CrashLoopBackOff. Console: pod → Details: Last State Terminated, reason OOMKilled, exit code 137. "The kernel killed it - no warning, no slowdown. That's memory." oc delete -f memory-hog.yaml. CPU: oc set resources deployment/guestbook --limits=cpu=100m. On the laptop: ab -k -c 10 -t 60 https://$(oc get route guestbook -o jsonpath='{.spec.host}')/ (keep -c at 10, as in demo 1). Pod → Metrics: CPU flat at the limit line. As peter, Observe → Metrics: rate(container_cpu_cfs_throttled_periods_total{namespace="demo-resources"}[1m]) - the throttling. "Nothing crashed - it just got slower. That's CPU." oc rollout undo deployment/guestbook. Talking point: with a CPU limit, an idle node still can't help a busy pod; with only a request, the pod is guaranteed its share and may use spare cycles.
