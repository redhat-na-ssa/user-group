From servers to OpenShift

The same questions - asked per container, answered by the platform

One slide to connect today's topic with what you already do with virtual machines. A VM can have physical CPU and memory reserved for it on the host - guaranteed, whatever else runs there. That's a request: the scheduler only places a pod where its requests fit. A VM is configured with a number of vCPUs and an amount of memory - the most the guest can ever use. That's a limit, enforced by the kernel on the node. Overcommit is the same idea too. A hypervisor lets you configure more vCPU and memory than the host physically has, betting that not every VM is busy at once. In OpenShift the requests must always fit the node - those are guaranteed - and the room between a pod's request and its limit is the overcommitted part: shared with every other pod on the node, first come, first served. Departments get budgets and disk quotas; projects get quotas. Monitoring is built in. And when an application needs more, you don't open a ticket to resize its server: the HPA adds copies under load and removes them after, and the VPA recommends the right size from what it really uses (Part 6). This slide is about applications running as containers; a VM running in OpenShift is resized the way you resize VMs today (Part 7). Requests

What a container is guaranteed.
The scheduler only places a pod where its requests fit.

In the demo: Parts 1 and 2

A request is a reservation. The scheduler adds up the requests of the pods already on each node and only places a new pod where its requests still fit in the node's allocatable capacity - the node's size minus what's kept back for the operating system and the kubelet. It doesn't look at actual usage at all. Two consequences. A pod with no requests can land anywhere, even on a full node. And a request that's far too big wastes capacity: the cluster looks full on paper while the processors sit idle. That gap between reserved and used is the first thing we'll look at in the demo.

Limits

The ceiling a container can't pass.
Enforced by the kernel, on the node.

In the demo: Parts 2 and 3

A limit is a hard cap, enforced by Linux cgroups on the node - the same mechanism you may already use on servers. Between its request and its limit, a container can use whatever happens to be free on the node. Above the limit, it's stopped - and how it's stopped depends on the resource, which is the next slide. Limits are optional. A container with a memory limit but no CPU limit is a common and sensible choice; we'll see why in Part 3.

One pod, three numbers

A node's memory - and where one pod's used, min and max sit in it

One node, seen from the memory side. The whole box is the node's physical memory. A slice on the left is kept back for the operating system and the kubelet; the rest is allocatable - what pods can reserve. Other pods have already reserved their share. Our guestbook pod has three numbers. Used: what it holds right now. Min, the request: memory guaranteed to it, and the only number the scheduler looks at when it places the pod - the solid part of the box is what it took from the node. Max, the limit: the pod may grow into the dashed part, but that room isn't reserved - it's shared with every other pod on the node, first come, first served. That's overcommit. If the pod goes past its limit, the kernel kills it: OOMKilled. And if the node runs short while the pod is in that shared room, it's among the first to be evicted. Set the request to what the pod really needs, and for anything important, request equal to limit removes the shared part altogether. The values are the ones the guestbook gets in Part 2 (used is an example). In the demo: Parts 1, 2 and 3.

CPU bends, memory breaks

Too much CPU: the container is slowed down.
Too much memory: it's killed.

In the demo: Part 3

CPU is a compressible resource: if a container wants more than its limit, the kernel simply gives it less time - it gets slower but keeps running. Memory isn't compressible: you can't take memory back from a process, so a container that goes over its memory limit is killed - the famous OOMKilled, exit code 137 - and restarted. That's also why overcommit works differently for the two. Requests are guaranteed; everything between a pod's request and its limit is shared room on the node, and the limits together can add up to more than the node has. For CPU that's harmless: busy containers just share. For memory, if several pods use that shared room at once, the node runs out and starts evicting pods that are over their requests. Common advice: for databases and anything that matters, set the memory request equal to the limit.

Quality of service

How requests and limits are set decides who goes first when a node runs short

Guaranteed

requests = limits

CPU and memory, every container. Evicted last.

Burstable

requests < limits

A reservation, plus room to grow. The usual choice.

BestEffort

nothing set

No reservation at all. Evicted first.

Eviction

node under pressure

BestEffort, then Burstable over their requests, then the rest.

In the demo: Parts 1 and 2

OpenShift sorts every pod into one of three quality-of-service classes, based only on how its requests and limits are set. Guaranteed: every container has CPU and memory requests equal to their limits. Burstable: at least a request is set, and limits are higher or missing - most applications. BestEffort: nothing set at all. The class matters when a node runs out of memory: the kubelet evicts BestEffort pods first, then Burstable pods that use more than they asked for. A pod that stays within its request is safe. Our guestbook starts the demo as BestEffort - the class nobody wants in production.

Quotas & limit ranges

A quota caps the whole project.
A limit range sets defaults and bounds per container.

In the demo: Part 4

A ResourceQuota caps the total for a project: CPU and memory requests and limits, number of pods, number of claims, storage per storage class. Anything that would take the project over its quota is refused when it's created - the existing pods keep running. A LimitRange works per container: it fills in a default request and limit for containers that don't set any, and rejects ones outside a minimum and maximum. The two go together: once a quota covers CPU or memory, every pod must state those values - the LimitRange's defaults make sure it does.

Scale out, not up

More small pods beat one big pod.
Let the autoscalers do the sizing.

In the demo: Part 6

The old reflex is to give an application one bigger machine. In OpenShift the better answer is usually more copies: a HorizontalPodAutoscaler adds pods when the average usage passes a target and removes them when load drops - so the cluster only reserves the extra capacity while it's needed. It also spreads the risk: losing one of six small pods hurts less than losing one big one. The VerticalPodAutoscaler looks at what pods actually use and recommends requests - an optional operator we only mention today. On clouds and some bare-metal setups the cluster autoscaler adds nodes when pods can't be scheduled. Cost Management, on console.redhat.com, gives the same kind of recommendations across clusters, with cost.

Virtual machines too

A VM runs inside a pod.
Its CPU and memory become that pod's requests.

In the demo: Part 7

With OpenShift Virtualization a virtual machine runs inside a pod called virt-launcher, so everything from today applies to VMs as well: the scheduler places them by their requests, quotas count them, and the same dashboards show their use. The translation has two defaults worth knowing. CPU is overcommitted: by default each vCPU requests a tenth of a core, because most VMs are idle most of the time (the ratio is a cluster setting). Memory is not overcommitted by default: the pod requests the guest's memory plus an overhead for the virtualization layer. Higher density through memory overcommit exists, but it's an opt-in. Measured on this cluster: a 2 vCPU, 2 GiB VM's pod requests 200m CPU and 2324Mi memory (2 GiB plus about 276Mi overhead).

2 · Requests and limits, the right way

Reserve what it really uses - cap the memory

  1. Deployment → Actions → Edit resource limits: CPU request 50m, memory request 320Mi, memory limit 512Mi, no CPU limit
  2. The form refuses - it insists on a CPU limit. Kubernetes doesn't: as code
  3. New pods: QoS Burstable
  4. Ask for far too much CPU: the new pod is Pending
  5. Roll back

The same, as code

oc patch deployment/guestbook \
  --patch-file=guestbook-resources.patch.yaml
oc get pods -o custom-columns=\
NAME:.metadata.name,QOS:.status.qosClass
oc set resources deployment/guestbook \
  --requests=cpu=100
oc get events --sort-by=.eventTime \
  --field-selector reason=FailedScheduling
oc rollout undo deployment/guestbook

3 · Hitting the ceiling

Over the CPU limit: slower. Over the memory limit: killed.

  1. A pod that keeps eating memory: OOMKilled, restarted
  2. Give the guestbook a tight CPU limit
  3. Put load on it: response times climb, throttling shows
  4. Roll back - and why many teams set no CPU limit

The same, as code

oc create -f memory-hog.yaml
oc get pod memory-hog -w
oc describe pod memory-hog | \
  grep -A 4 'Last State'
oc delete -f memory-hog.yaml

oc set resources deployment/guestbook \
  --limits=cpu=100m
ab -c 10 -t 60 https://$(oc get route \
  guestbook -o jsonpath='{.spec.host}')/
oc exec deployment/guestbook -- \
  grep throttled /sys/fs/cgroup/cpu.stat
oc rollout undo deployment/guestbook
As user3. oc create -f memory-hog.yaml - a small pod that allocates memory in a loop, with a 128Mi limit. oc get pod memory-hog -w: Running → OOMKilled → CrashLoopBackOff. Console: pod → Details: Last State Terminated, reason OOMKilled, exit code 137. "The kernel killed it - no warning, no slowdown. That's memory." oc delete -f memory-hog.yaml. CPU: oc set resources deployment/guestbook --limits=cpu=100m. On the laptop: ab -c 10 -t 60 https://$(oc get route guestbook -o jsonpath='{.spec.host}')/ (no -k: each request opens its own connection, so the router can send it to the least busy pod). Rehearsal numbers: without a limit about 290 requests/s at 35 ms, each pod using ~1.9 cores; with 100m about 11/s at 0.9 s - 26 times slower (2.6/s at 3.8 s with both pods on a Xeon D node and the background traffic running). Read "Requests per second", the first "Time per request" and "Non-2xx responses" (a request that waited 30 s for the router: the real failures). Ignore "Failed requests: Length": ab compares each reply's size with the first one it got, and if that was the router's 92-byte 504 page, every real 2251-byte page counts as "failed". The proof is in the kernel, not the graphs (they lag): oc exec deployment/guestbook -- cat /sys/fs/cgroup/cpu.max shows "10000 100000" - 10 ms of CPU per 100 ms period, which is what 100m means; grep throttled /sys/fs/cgroup/cpu.stat, run twice during the load, shows nr_throttled and throttled_usec climbing. oc adm top pods: CPU at 100m, never above. If asked why pods differ: the nodes aren't identical (low-power Xeon D vs EPYC) - the same request costs more CPU on one than the other; the Route sends each request to the pod with the fewest in flight. "Nothing crashed - it just got slower. That's CPU." oc rollout undo deployment/guestbook. Talking point: with a CPU limit, an idle node still can't help a busy pod; with only a request, the pod is guaranteed its share and may use spare cycles. Memory: request = limit for anything important. Press DOWN for the backup screenshots.

The guestbook under load with a CPU limit of a tenth of a core. Both need watching: a volume can fill up, and so can the pool that thin-provisioned volumes share.

  2. Load: more pods - not bigger ones
  3. Load gone: back to 2
  4. For the size: VPA and Cost Management recommend requests

6 · Optional: the VPA recommends the size

The HPA decides how many - the VPA how big

  1. VPA in Off mode: it recommends, changes nothing
  2. Compare it with the sizes we set in Part 2
  3. Optional: Initial mode - memory only, when a pod starts
  4. CPU stays with the HPA

The same, as code

oc describe vpa guestbook
oc patch vpa guestbook --type=merge \
  --patch-file=guestbook-vpa-initial.patch.yaml
oc rollout restart deployment/guestbook
OPTIONAL - only when there's time or the audience asks; RIGHT skips it. DRAFT, not rehearsed yet. The VPA was created by setup, not now: it recommends from usage history, so it has been watching the guestbook (and the background traffic) for days. The file is guestbook-vpa.yaml (cat it): target Deployment guestbook, updateMode "Off" - recommend only, it never touches a pod. "Off" is how you start. And memory only: CPU belongs to the HPA, which scales on CPU as a percentage of the request - a VPA changing that request would fight it. Rule: HPA for CPU, VPA for memory. As user3: oc get vpa guestbook (MEM column: the target, in bytes - 476450463 is about 454Mi; CPU stays empty), then oc describe vpa guestbook → Status, Recommendation: Lower Bound, Target, Upper Bound per container. Compare with Part 2's 320Mi: "measured over days, not one rehearsal". The cluster sets a floor (250Mi memory): the recommendation never goes below it. Console: Search → VerticalPodAutoscaler → guestbook → YAML, the status at the bottom. Optional, apply it: oc patch vpa guestbook --type=merge --patch-file=guestbook-vpa-initial.patch.yaml - mode "Initial": set requests when a pod is created, never restart one. "Restart" means new pods, and new pods are where the VPA steps in: oc rollout restart deployment/guestbook and oc get pods -l app=guestbook -o jsonpath='{.items[*].spec.containers[0].resources}': the memory request is the VPA's target, and the limit moved with it (same ratio as 320Mi/512Mi); CPU is still Part 2's 50m. Rehearsal (2026-11-24): ~454Mi after one minute of history, ~392Mi an hour later; re-check it before the session. The pod's vpaUpdates annotation says the VPA did it. The catch: oc get deployment guestbook still says 320Mi - the VPA changes pods, not the Deployment, so the YAML (and Git, and Argo CD) no longer describe what runs. Another reason to start with "Off" and copy the number into the Deployment yourself. The modes, as an escalation: Off → Initial → InPlace / Recreate - from looking, to sizing new pods, to changing running ones (InPlace resizes a running pod without a restart, Recreate evicts it, InPlaceOrRecreate tries the first and falls back to the second; Auto is the old name for Recreate). Say it out loud: a VPA with no updateMode is Recreate - it starts evicting pods. That's why guestbook-vpa.yaml sets "Off".

7 · Virtual machines: the same rules

A VM's CPU and memory - as the scheduler sees them

  1. Start a VM: 2 vCPU, 2 GiB
  2. Its virt-launcher pod: the requests behind it
  3. CPU overcommitted by default, memory not
  4. The project's quota counts the VM too

The same, as code

virtctl start small-vm
oc get vm,vmi
oc get pod -l kubevirt.io=virt-launcher \
  -o jsonpath='{.items[0].spec.containers[0].resources}'
oc describe quota
As peter. Setup created small-vm stopped (it holds nothing until it runs). Virtualization → VirtualMachines → small-vm → Start (or virtctl start small-vm); it boots in under a minute. oc get vm,vmi. Its pod: oc get pod -l kubevirt.io=virt-launcher -o jsonpath='{.items[0].spec.containers[0].resources}' - CPU request a tenth per vCPU (200m), memory request the guest's 2Gi plus overhead (2324Mi). And a memory limit of 4648Mi nobody wrote: because the project's quota has limits.memory, OpenShift Virtualization sets one itself (twice the request), or the quota would refuse the pod. "The scheduler sees a pod - the same rules as every other workload." Administration → ResourceQuotas: the VM counts against the quota. The quota shows the project's total, not the VM: Used grows by the VM pod's 2324Mi request and 4648Mi limit (plus 1M / 40M for a KubeVirt helper container). oc describe quota shows the memory in bytes (Mi and KubeVirt's decimal M don't add up to a round number) - the console page reads better. Read the VM's own numbers from its pod, above. Stop the VM afterwards (virtctl stop small-vm) - or after the optional "same network" step below (DOWN). If asked "can the HPA or VPA scale a VM?": no. A VM is one virt-launcher pod; more pods would be more VMs, not a bigger one. A VM is resized the VM way - edit its CPU and memory; a live migration applies it to the running VM (at the next restart if it can't migrate). Slide 5 says the same. The cluster-wide knobs (admin, look only): the HyperConverged resource's CPU allocation ratio, and the opt-in memory overcommit for higher density. The VM started in Part 7 runs the same guestbook as the pods, installed by cloud-init at boot (dnf: psql, Flask; app.py from Gitea - the same source). It's ready about a minute after the start, so by now it is. As peter: oc get vmi small-vm - its IP is on the pod network; oc get pods -o wide - the guestbook pods' IPs, same range. What we just did

The plan from the start - in OpenShift terms

  • Usage vs requests: QoS classes, dashboards, node allocation
  • Requests from measurements, a memory limit, no CPU limit
  • CPU throttling vs OOMKilled - overcommit
  • ResourceQuota and LimitRange per project
  • PVC usage and storage capacity
  • HPA scale-out - VPA and Cost Management for sizing
  • VM resources through virt-launcher pods
The same seven points as "What we will cover today", with the names you saw on screen. A pod without requests is BestEffort and invisible to the scheduler's accounting; requests come from measured use, memory gets a limit, CPU usually doesn't. Over a CPU limit a container is throttled; over a memory limit it's OOMKilled - which is why CPU is safe to overcommit and memory isn't. Quotas and limit ranges are the project's ceiling and defaults; volumes and the storage behind them both need watching; the HPA adds copies under load, and the VPA and Cost Management recommend sizes; and VMs follow the same rules through their pods.
