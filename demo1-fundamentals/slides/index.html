Part one

OpenShift architecture 1:1

Ten words we'll use for the rest of the session

One idea per slide. Every term will show up again in the demo - the small line under each picture says where, so point back to it later.

Cluster

Control plane runs the cluster.
Workers run your apps.

In the demo: the admin's Nodes page

A cluster is a set of machines managed as one. The control plane is the brain: the API server everyone talks to (console, oc, pipelines), etcd storing the desired state, the scheduler deciding where things run, and controllers that keep reality matching the desired state. Worker nodes run the actual applications (the small teal boxes are pods - next slides). Developers never log in to these machines.

Node

A machine - VM or bare metal - that runs pods.

In the demo: the "Node" field on every pod

A node is just a machine in the cluster. On OpenShift it runs RHEL CoreOS, a container runtime (CRI-O) and the kubelet, which starts the pods the scheduler assigned to it. The scheduler places pods where there's capacity; you'll see the node name on every pod in the console.

Container image

Your app plus everything it needs. Immutable. Stored in a registry.

In the demo: the pipeline builds one

An image packages the application with its runtime and dependencies, in layers. Once built it never changes - a new version is a new image. Images live in a registry: OpenShift has one built in, and there's quay.io and friends outside. "Works on my machine" becomes "works everywhere the image runs".

Pod

One or more containers, one IP, shared storage.
Small, and disposable.

In the demo: Part 2

The pod is the smallest thing OpenShift runs. Usually one container, it gets its own IP address and can mount storage. Pods are cattle, not pets: they come and go, get rescheduled, get replaced. Never rely on a pod's IP - that's what Services are for.

Deployment

"Keep N copies of this pod running."
Change it, and it rolls out.

In the demo: every part

A Deployment is desired state: this image, this configuration, this many replicas. Controllers make it true and keep it true - delete a pod and a replacement appears. Change the image or the configuration and it rolls out a new ReplicaSet, replacing pods gradually, and keeps the old one around so you can roll back.

Service

A stable name and address in front of changing pods.

In the demo: the guestbook finds postgresql by name

Pods come and go and their IPs change. A Service gives a set of pods (picked by label) one stable name and virtual IP, and load-balances across them. Other apps just use the name: our guestbook connects to "postgresql" - cluster DNS does the rest. Services are internal to the cluster.

Route

A public HTTPS address for a Service.

In the demo: the app URL

Services are only reachable inside the cluster. A Route publishes one to the outside world with a hostname, through the OpenShift router, and usually terminates TLS for you. (Kubernetes Ingress does the same job; Routes are OpenShift's older, richer version.)

Project

A namespace: names, quotas, network - and who may do what.

In the demo: Part 5

A project is a Kubernetes namespace with some OpenShift extras. It's the boundary for names, quotas and network policy - and for access. Access is role-based: standard roles (admin, edit, view) are bound to users or groups per project. Our demo project has an admin, a developer and a viewer.

ConfigMap & Secret

Configuration and credentials, kept outside the image.

In the demo: Parts 1, 3 and 7

Same image in dev, test and prod - what changes is configuration. A ConfigMap holds plain settings, a Secret holds credentials (and has tighter access: our viewer can't read it). Both are injected into pods as environment variables or files. Changing them doesn't rebuild the image.

Pipeline

Automated steps from source code to running app. Each step is a pod.

In the demo: Parts 3 and 6

A pipeline is a series of tasks - clone the code, build an image, deploy it - and every task runs as a pod in the cluster, like any other workload. OpenShift Pipelines is based on the Tekton project. A commit can start it automatically; you'll see that in Part 5.

2 · Containers and pods

Look inside - then see what a bare pod is worth

  1. The database pod: Details, Logs, Terminal, Events
  2. +Add → Import YAML: a pod is a name and an image
  3. Delete it - nothing brings it back
  4. Delete the database pod - it comes back

The same, as code

oc rsh deployment/postgresql psql -c '\l'
oc apply -f hello-pod.yaml
oc delete pod hello
oc delete pod -l app=postgresql
oc get pods
Topology → postgresql → the pod. Details: pod IP and Node (tie back to the slide). Logs: the database starting. Terminal: psql -c '\l' - you're inside the running container; id - a random high UID, not root. Events: scheduled → volume attached → pulled → started. +Add → Import YAML, paste manifests/hello-pod.yaml, Create: "this is all a pod is - a name and an image". Actions → Delete Pod: gone for good. Contrast: delete the PostgreSQL pod - its Deployment replaces it within seconds, and the data survives on the PVC. Press DOWN for backup screenshots.

3 · From source code to running app

Import from Git - with a pipeline

  1. +Add → Import from Git - Gitea Service URL
  2. Python 3.12 · app guestbook · build: Pipelines
  3. Watch the pipeline: fetch → build → deploy
  4. "Database unavailable" → map the Secret

Credentials, as code

oc patch deployment/guestbook \
  --patch-file=guestbook-db-env.patch.yaml

# env:
#   - name: POSTGRESQL_USER
#     valueFrom:
#       secretKeyRef:
#         name: postgresql
#         key: database-user
Git Repo URL: http://local-gitea.gitea.svc:3000/ocpdemo/guestbook.git - the yellow "repository is unreachable" warning is expected: the console checks from outside the cluster, the pipeline clones from inside. Choose Builder Image → Python 3.12-ubi9 by hand. Application guestbook, Name guestbook (must be exactly that - the push trigger uses it). Build option Pipelines. Resource type Deployment. Create. Talk through the build (~90 s): PipelineRun graph (each box is a pod on a node) → fetch-repository logs (cloned via the in-cluster Service) → build logs (no Dockerfile; image pushed to the internal registry) → Topology: the Deployment exists and waits for its image → Service and Route already there → deploy turns green. App shows "password authentication failed": the app reached postgresql by Service name but has no credentials. Show ONE row in the Deployment's Environment tab (full page): POSTGRESQL_USER → secret postgresql → key database-user - "the name is what the app reads, the key is where the Secret keeps it". Reload - "twenty variables, three environments?" - then in the web terminal: oc patch deployment/guestbook --patch-file=guestbook-db-env.patch.yaml New pod rolls out. Refresh, sign the guestbook. Env vars keep it simple today; in production mount files or use a vault / External Secrets Operator. Press DOWN for backup screenshots.

4 · Self-healing and scaling

Declare it - OpenShift keeps it true

  1. Add Health Checks: /readyz, /healthz
  2. Delete the pod - a new one starts
  3. Scale to 3 - one Service, three endpoints
  4. Sticky sessions → round robin

The same, as code

oc delete pod -l deployment=guestbook
oc scale deployment/guestbook --replicas=3
oc patch route/guestbook \
  --patch-file=guestbook-route-roundrobin.patch.yaml
Topology → guestbook → Actions → Add Health Checks. Readiness: HTTP GET /readyz port 8080 ("only send traffic once the pod can reach the database"). Liveness: HTTP GET /healthz port 8080, initial delay 10 ("restart it if the process hangs"). Add → another rollout. Delete the pod → replacement straight away. Details → up arrow → 3 pods. Refresh: same pod every time. Sticky sessions in 10 seconds: "the router sets a cookie so your browser keeps hitting the same pod - good for apps with in-memory sessions; ours keeps everything in the database, so any pod can answer." Then: oc patch route/guestbook --patch-file=guestbook-route-roundrobin.patch.yaml Refresh in a new private window a few times - the pod name changes. Press DOWN for backup screenshots.

6 · A commit becomes a new version

No tickets, no manual redeploy

  1. +Add → Import YAML: the EventListener
  2. Gitea: VERSION = "2.0" → commit
  3. Pipelines: a run started by itself
  4. Refresh: v2.0 - the data is still there

The same, as code

oc apply -f guestbook-eventlistener.yaml
git commit -am "Release v2.0" && git push
oc get pipelineruns -w
oc rollout status deployment/guestbook
First the listener: +Add → Import YAML, paste manifests/guestbook-eventlistener.yaml, Create. el-guestbook appears in Topology: "the endpoint Gitea calls on every push - it checks the webhook secret and starts our pipeline. Part of OpenShift Pipelines (Tekton Triggers); just another Deployment." Wait for the blue ring. In Gitea (ocpdemo/guestbook): app.py → Edit → VERSION = "2.0" → commit to main. Pipelines: a new PipelineRun "guestbook-push-..." started on its own - Gitea called el-guestbook, which started the run. Watch Topology: new pods only take traffic after the readiness check from Part 4 passes. Refresh: v2.0, all entries still there. Fallback if nothing starts in ~10 s: Pipelines → guestbook → Actions → Start. Afterwards check Gitea → Settings → Webhooks → Recent deliveries. Press DOWN for backup screenshots.

7 · Configuration and rollback

Configuration is part of the Deployment too

  1. Environment: APP_COLOR, APP_TITLE
  2. Refresh - blue banner, no rebuild
  3. ReplicaSets: one per revision
  4. Roll back

The same, as code

oc set env deployment/guestbook \
  APP_COLOR='#0066cc' \
  APP_TITLE='Guestbook - config change'
oc rollout history deployment/guestbook
oc rollout undo deployment/guestbook
Topology → guestbook → the Deployment name (full page) → Environment → Add more: APP_COLOR = #0066cc, APP_TITLE = Guestbook - config change → Save. Refresh: blue. ReplicaSets tab: one per revision. Roll back in the web terminal: oc rollout undo deployment/guestbook. Refresh: red v2.0 again. (Env vars roll out automatically; a ConfigMap change would not - that's one reason we use env here.)
