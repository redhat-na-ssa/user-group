What is OpenShift?

Kubernetes - plus everything you need to run applications on it

One slide, one idea: OpenShift is Kubernetes, packaged and supported by Red Hat, with the pieces you'd otherwise have to choose, install and glue together yourself - the web console, pipelines, an image registry, the router that publishes apps, a curated catalog, and security and access control built in. It runs on Red Hat Enterprise Linux CoreOS, on bare metal, virtual machines or any major cloud, and it looks the same everywhere. Everything we're about to do in the demo is a standard Kubernetes object under the hood - the console just makes it visible. If the audience is new to the vocabulary (pod, Deployment, Service, Route...), press DOWN for one slide per term; otherwise go RIGHT straight into the demo and explain the words as they appear on screen.

Cluster

Control plane runs the cluster.
Workers run your apps.

In the demo: pods spread across the workers

A cluster is a set of machines managed as one. The control plane is the brain: the API server everyone talks to (console, oc, pipelines), etcd storing the desired state, the scheduler deciding where things run, and controllers that keep reality matching the desired state. Worker nodes run the actual applications (the small teal boxes are pods - next slides). Developers never log in to these machines.

Node

A machine - VM or bare metal - that runs pods.

In the demo: the "Node" field on every pod

A node is just a machine in the cluster. On OpenShift it runs RHEL CoreOS, a container runtime (CRI-O) and the kubelet, which starts the pods the scheduler assigned to it. The scheduler places pods where there's capacity; you'll see the node name on every pod in the console.

Container image

Your app plus everything it needs. Immutable. Stored in a registry.

In the demo: the pipeline builds one

An image packages the application with its runtime and dependencies, in layers. Once built it never changes - a new version is a new image. Images live in a registry: OpenShift has one built in, and there's quay.io and friends outside. "Works on my machine" becomes "works everywhere the image runs".

Pod

One or more containers, one IP, shared storage.
Small, and disposable.

In the demo: Part 2

The pod is the smallest thing OpenShift runs. Usually one container, it gets its own IP address and can mount storage. Pods are cattle, not pets: they come and go, get rescheduled, get replaced. Never rely on a pod's IP - that's what Services are for.

Deployment

"Keep N copies of this pod running."
Change it, and it rolls out.

In the demo: every part

A Deployment is desired state: this image, this configuration, this many replicas. Controllers make it true and keep it true - delete a pod and a replacement appears. Change the image or the configuration and it rolls out a new ReplicaSet, replacing pods gradually, and keeps the old one around so you can roll back.

Service

A stable name and address in front of changing pods.

In the demo: the guestbook finds postgresql by name

Pods come and go and their IPs change. A Service gives a set of pods (picked by label) one stable name and virtual IP, and load-balances across them. Other apps just use the name: our guestbook connects to "postgresql" - cluster DNS does the rest. Services are internal to the cluster.

Route

A public HTTPS address for a Service.

In the demo: the app URL

Services are only reachable inside the cluster. A Route publishes one to the outside world with a hostname, through the OpenShift router, and usually terminates TLS for you. (Kubernetes Ingress does the same job; Routes are OpenShift's older, richer version.)

Project

A namespace: names, quotas, network - and who may do what.

In the demo: Part 5

A project is a Kubernetes namespace with some OpenShift extras. It's the boundary for names, quotas and network policy - and for access. Access is role-based: standard roles (admin, edit, view) are bound to users or groups per project. Our demo project has an admin, a developer and a viewer.

ConfigMap & Secret

Configuration and credentials, kept outside the image.

In the demo: Parts 1, 3 and 7

Same image in dev, test and prod - what changes is configuration. A ConfigMap holds plain settings, a Secret holds credentials (and has tighter access: our viewer can't read it). Both are injected into pods as environment variables or files. Changing them doesn't rebuild the image.

Pipeline

Automated steps from source code to running app. Each step is a pod.

In the demo: Parts 3 and 6

A pipeline is a series of tasks - clone the code, build an image, deploy it - and every task runs as a pod in the cluster, like any other workload. OpenShift Pipelines is based on the Tekton project. A commit can start it automatically; you'll see that in Part 6. Last concept slide: press RIGHT to go to the demo.

4 · Self-healing and scaling

Declare it - OpenShift keeps it true

  1. Add Health Checks: /readyz, /healthz
  2. Delete the pod - a new one starts
  3. Scale to 3 - one Service, three endpoints
  4. Sticky sessions → round robin
  5. CPU request, then Add HorizontalPodAutoscaler
  6. Load with ab: 2 → 6 pods, and back

The same, as code

oc delete pod -l deployment=guestbook
oc scale deployment/guestbook --replicas=3
oc patch route/guestbook \
  --patch-file=guestbook-route-roundrobin.patch.yaml
oc set resources deployment/guestbook \
  --requests=cpu=50m,memory=320Mi --limits=memory=512Mi
oc apply -f guestbook-hpa.yaml
ab -k -c 10 -t 120 https://guestbook-demo-intro.apps…/
oc get hpa guestbook -w
Topology → guestbook → Actions → Add Health Checks. Readiness: HTTP GET /readyz port 8080 ("only send traffic once the pod can reach the database"). Liveness: HTTP GET /healthz port 8080, initial delay 10 ("restart it if the process hangs"). Add → another rollout. Delete the pod → replacement straight away. Details → up arrow → 3 pods, on different worker nodes (each pod's Node field) - one machine failing doesn't take the app down. Refresh: same pod every time. Sticky sessions in 10 seconds: "the router sets a cookie so your browser keeps hitting the same pod - good for apps with in-memory sessions; ours keeps everything in the database, so any pod can answer." Then: oc patch route/guestbook --patch-file=guestbook-route-roundrobin.patch.yaml Refresh in a new private window a few times - the pod name changes. Autoscaling. First, what each pod asks for: oc set resources deployment/guestbook --requests=cpu=50m,memory=320Mi --limits=memory=512Mi "The autoscaler measures CPU as a percentage of the request, so it needs one." Another rollout. (Same fields in the console: the Deployment's Actions → Edit resource limits.) Then in the console: Topology → guestbook → Actions → Add HorizontalPodAutoscaler: min 2, max 6, CPU utilization 50% → Save. "From now on the autoscaler owns the replica count - my manual 3 will drop to 2." Then the same as code, which can say more than the form: oc apply -f guestbook-hpa.yaml (adds a 1-minute scale-down window instead of the default 5, so we see the pods go away again). Load, from the laptop terminal (not the web terminal - ab is local): ab -k -c 10 -t 120 https://guestbook-demo-intro.apps.homeocp.ocp4.peterlarsen.org/ oc get hpa guestbook -w in a second terminal, and watch Topology: CPU jumps far above 50%, and within ~30 s the ring goes from 2 to 6 pods. When ab ends (2 min), CPU drops and about a minute later it's back to 2. Keep -c at 10: 50 concurrent requests queue behind the health checks, pods turn Not Ready, and the autoscaler stops seeing them. Press DOWN for backup screenshots.
Backup

Health checks: readiness and liveness

oc set probe deployment/guestbook --readiness \
  --get-url=http://:8080/readyz --period-seconds=5

oc set probe deployment/guestbook --liveness \
  --get-url=http://:8080/healthz --initial-delay-seconds=10
Two questions OpenShift now asks every guestbook pod. Readiness (/readyz, every 5 s): can you take traffic - the app answers yes only once it can reach the database; until then the Service sends it no requests. Liveness (/healthz, every 10 s, starting after 10 s): are you still alive - after 3 failures in a row the container is restarted. Defaults not on the slide: 3 failures in a row count as failed, each check times out after 1 s. In the console these are the Readiness and Liveness sections of Actions → Add Health Checks (path /readyz for readiness, /healthz for liveness, port 8080). Adding them changes the pod template, so it's another rollout.
Backup

Scaling by hand: one click, three pods

The guestbook Deployment's Details tab after pressing the up arrow twice: 3 pods. The arrows change one number - replicas - and the Deployment makes it true, starting pods (on different workers) until the ring is full. The Service now spreads requests over all three. As code: oc scale deployment/guestbook --replicas=3. Once the autoscaler is added later in this part, these arrows disappear and the ring says "Autoscaled to N Pods": the autoscaler owns the number from then on.
Backup

Three pods, three different workers

The Deployment's Pods tab right after scaling (Node column added with the column picker). Three pods, each with its own name, all Running and Ready - one created a couple of minutes ago by the scale-up. The Node column is the point: the scheduler put each pod on a different worker, so one machine failing doesn't take the app down. Same picture as the Cluster slide at the start. Autoscaling under load: 2 → 6 pods, and back to 2

oc get hpa guestbook -w during the ab run. Read it top to bottom: idle at 6-8% of the CPU target with 2 pods; ab starts and CPU jumps to 4448% of the target (each pod using far more than its 50m request); the autoscaler grows the Deployment to 6 pods (the maximum); as the load is spread and then stops, CPU falls back to single digits; a minute later (the scale-down window in guestbook-hpa.yaml) it's back to 2. Nobody touched the replica count - the autoscaler owns it now.

6 · A commit becomes a new version

No tickets, no manual redeploy

  1. Terminal: create the EventListener
  2. Gitea: VERSION = "2.0" → commit
  3. Pipelines: a run started by itself
  4. Refresh: v2.0 - the data is still there

The same, as code

oc create -f guestbook-eventlistener.yaml
git commit -am "Release v2.0" && git push
oc get pipelineruns -w
oc rollout status deployment/guestbook
First the listener, in the terminal: oc create -f guestbook-eventlistener.yaml el-guestbook appears in Topology: "the endpoint Gitea calls on every push - it checks the webhook secret and starts our pipeline. Part of OpenShift Pipelines (Tekton Triggers); just another Deployment." Wait for the blue ring. In Gitea (ocpdemo/guestbook): app.py → Edit → VERSION = "2.0" → commit to main. Pipelines: a new PipelineRun "guestbook-push-..." started on its own - Gitea called el-guestbook, which started the run. Watch Topology: new pods only take traffic after the readiness check from Part 4 passes. Refresh: v2.0, all entries still there. What changed? oc rollout history deployment/guestbook - one revision per change, CHANGE-CAUSE (Deployments don't record why). Diff the newest two revisions (cheat 6): only the image digest differs - "a new digest means a build caused this rollout; the why is the commit message in Git". Fallback if nothing starts in ~10 s: Pipelines → guestbook → Actions → Start. Afterwards check Gitea → Settings → Webhooks → Recent deliveries. Press DOWN for backup screenshots.

What we just did

The plan from the start - in OpenShift terms

  • Catalog & template - a database in one form
  • Pod - logs, terminal, events
  • Pipeline - source → image → Deployment, Service, Route
  • Deployment - self-healing, scaling, health checks
  • Project & RBAC - who can do what
  • Webhook → pipeline → rollout - and rollback
The same six points as "What we will cover today", now with the names you saw on screen: a template from the catalog gave us the database; we looked inside its pod; a pipeline turned source code into an image and a Deployment, with a Service and a Route in front; the Deployment healed and scaled itself; the project and its roles decided who could do what; and a commit in Git rolled out a new version, which we rolled back.
